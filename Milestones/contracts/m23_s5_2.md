## Objective

Implement the **persistence adapter** for the accepted pure S5.1 joint entity-accession core — the
accession-side analogue of `src/disclosure_drift/sec/entity_selection_store.py` (S4.2). It reads
frozen candidate rows, validates their canonical forms and stored hashes, converts them into the
accepted S5.1 immutable inputs, derives a deterministic content-derived run identity, invokes the
accepted pure solver, persists the result transactionally, and reconstructs it idempotently.

§§5.3, 6, 17, 18, 19, 20, 21, 27, 28, and §29's ownership table, within the unchanged Decision 013 §5
objective and the unchanged Decision 016 §5 run lifecycle — and by
[Decision 019](../../Docs/Decisions/decision_019_m23_s5_storage_to_pure_input_mapping.md) (approved
2026-07-28) for the four storage-to-pure-input mappings the conversion step depends on.

### `INSERT OR REPLACE` ruling

This distinction is deliberate and must not be collapsed:

- **Authorized, for migration `0011` only:** `INSERT OR REPLACE INTO reference_policy_versions`.
  This is the literal accepted convention of migration `0010`, and Decision 018 §20 directs `0011` to
  seed its value "using the accepted migration `0010` pattern". It is what makes the migration
  idempotent under rerun. **Migration `0011` remains an INSERT-only migration for governance
  purposes because it performs no schema mutation** — "INSERT-only" here means "no DDL", and the
  replace clause is a conflict-resolution behavior on a reference row, not a schema change.
- **Prohibited everywhere else:** `INSERT OR REPLACE`, destructive replacement, delete-and-recreate
  behavior, and destructive upserts are prohibited for **runtime lifecycle, selection, quota,
  diagnostic, and result persistence**. A duplicate same-ID insertion follows the deterministic gate
  convention below; it is never silently overwritten.

## Run identity

S5.2 derives a **content-derived `selection_run_id`** for the S5 joint run, distinct from the S4
draft's (Decision 018 §6). S5.1 reports normalized inputs but persists no identity; identity
construction is S5.2's.

**Must include:**

- the joint selector policy version;
- the selection seed;
- the required positive `node_limit` (Decision 018 §17: the limit enters run identity);
- the complete normalized frozen entity-candidate content;
- the complete normalized frozen accession-candidate content;
- the material frozen quota-policy and policy-reference inputs;
- the repository's canonical serialization version/convention — `release/hashing.py`'s `hash_table`
  and an explicit input-schema version string, following the accepted S4.2 precedent
  (`ENTITY_SELECTION_INPUT_SCHEMA_VERSION`, `build_entity_selection_run_identity`).

**Must exclude** (Decision 016 §8, Decision 018 §26): every timestamp and wall-clock read; process
identity; filesystem paths; database row order; insertion order; Python object representations;
mutable lifecycle state; the S4 entity-only selection result and the S4 `selection_run_id`; and any
outcome or future information.

**Required properties:**

- a permutation of semantically identical database rows produces the **same** run ID;
- **any** material input or policy change — including `node_limit`, the seed, the policy version, and
  any candidate content change — produces a **different** run ID.

## Reconstruction representation

- The accepted pure result is reconstructed as `accession_selector.JointSelectionResult`.
- The store module **may define exactly one** separate frozen, immutable run-metadata wrapper
  containing: `selection_run_id`; snapshot and policy provenance; execution inputs (selection seed
  and node limit); and the reconstructed `JointSelectionResult`. Structural precedent:
  `entity_selection_store.PersistedEntitySelectionResult`.
- The wrapper **must not duplicate or reinterpret S5.1 methodology** — it carries provenance and the
  pure result, and derives no methodological value of its own.
- **Database rows are never represented inside S5.1.** No database-shaped substitute type is added
  to the pure core.
- **Persisted corruption is never silently normalized.** Reconstruction validates lifecycle status,
  policy version, run-identity inputs, selected entity counts and categories, accession roles,
  `selected_order` density and uniqueness, canonical identity and stored-hash consistency, objective
  fields and vectors, quota identifiers and deterministic ordering, absence of selected rows on
  non-feasible outcomes, deferred-quota semantics, expanded-node and exhaustion consistency, and
  foreign-key integrity. A corrupted, incomplete, contradictory, or policy-mismatched persisted run
  **fails closed**.

## Lifecycle rulings

Within the unchanged Decision 016 §5 lifecycle vocabulary:

- **The S4 entity-only draft remains unchanged**: it stays in `running` state, remains
  non-publishable, and is never mutated, promoted, deleted, transformed into the S5 run, used as
  manifest input, or treated as the fixed entity set for the joint run (Decision 018 §6, §27). A
  permanently-`running` S4 draft is expected residue, not an abandoned run.
- **S5 creates a distinct new lifecycle record** with its own content-derived ID.
- **Same-ID behavior** (Decision 018 §18):
  - an existing **complete, valid** result is reconstructed and returned **idempotently**, only when
    every persisted component validates against the frozen policy and input identity;
  - an existing `failed` record **gate-fails**;
  - an existing `planned` record **gate-fails**;
  - an existing incomplete `running` record **gate-fails**;
  - **no automatic retry**; **no S5 retry entry point**; Decision 016 §5's `failed -> running`
    transition stays defined in the schema and is exercised by no S5 module;
  - **no new ID may be manufactured** to bypass a same-ID failure;
  - manual recovery remains deferred and separately authorized.
- **Node-limit exhaustion**: status `infeasible_or_unproven`, `node_limit_exhausted` recorded, every
  incumbent discarded, **no selected entity or accession rows persisted**, no incumbent exposed, and
  never a partial approved selection (Decision 018 §17, §28).
- **Proven infeasibility** likewise persists no selected rows and no partial objective.
- **One explicit transaction per new run attempt**, guaranteeing: the lifecycle row and all result
  rows cannot disagree; a feasible run commits only with its complete selected entities, selected
  accessions, selected order, objective components, quota results, diagnostics, and required
  provenance; a non-feasible run contains no selected rows; exceptions roll back partial writes;
  foreign keys remain enabled; and reconstruction after commit exactly reproduces the persisted
  result.
- **No commit, push, or tag before S5.3 acceptance** — see "Commit boundary".
