## Selected-versus-reserve boundary

- A reserve **never** alters, replaces, or reorders any selected entity or accession. Selection is
  settled by S5.1 before any reserve exists.
- A reserve is **constructed**, never **applied**. Substitution is an M2.5 event outside this stage.
- The replacement entity is not itself selected in the same run, and `target <> replacement`.
- **Every selected entity is a reserve target, including the four boundary controls.** Compatibility
  alone decides whether a valid reserve exists; entity role never does.
- **Exactly one reserve package per target, at `reserve_rank = 1`.** Multiple ranks are not
  authorized at M2.3.
- **A replacement CIK may serve different targets.** Packages are independent contingencies and are
  never simultaneously applied. Within one target a replacement CIK appears at most once. **No global
  replacement uniqueness, cross-target assignment problem, greedy pool consumption,
  target-order-dependent allocation, or pool-exhaustion state may be introduced** — each target's
  reserve is computed independently, so no result may depend on the order targets are processed.
- Reserves are never published and are not a manifest input before Stage S6.

## Quota-contribution membership boundary

## Schema and migration ruling

**For reserves, contributions, and quota members: no DDL and no migration.** Every table, column,
constraint, index, and trigger those families need already exists in migration `0009`. The signature
policy constant `PILOT_REPLACEMENT_SIGNATURE_POLICY_VERSION` and its `pilot_replacement_signature`
reference row both already exist, so unlike Stages S4 and S5.2 this stage adds no policy-reference
migration. Registering `REVIEW_PILOT_NO_COMPATIBLE_RESERVE` also needs none: `reference_reason_codes`
is seeded at runtime from `reasons.py`.

**For the durable no-compatible-reserve record: exactly one migration, `0012`, is authorized in
principle** — `src/disclosure_drift/storage/migrations/0012_m23_selection_entity_reasons.sql`.
Migration `0009` has no lawful location for that record (Decision 020 §8.1), so the owner authorized
`0012` rather than weakening the durability requirement. Its design is frozen by Decision 020 §8.2:

- **exactly one new `STRICT` table**, `pilot_selection_entity_reasons`, carrying `selection_run_id`,
  `snapshot_id`, `cik_numeric`, `reason_scope`, `reason_code`, and `recorded_at_utc`; a composite
  foreign key to `pilot_selected_entities (selection_run_id, snapshot_id, cik_numeric)`; a
  `reference_reason_codes` foreign key on `reason_code`; a primary key of
  `(selection_run_id, snapshot_id, cik_numeric, reason_scope)` that makes a duplicate disposition row
  structurally impossible; and no `detail` column, so no free-text value forms part of the disposition;
- **three lifecycle guards whose complete SQL is frozen in Decision 020 §8.2** — INSERT, UPDATE, and
  DELETE. They are **not** mirrors of migration `0009`'s guards. Each uses an explicit
  `NOT EXISTS (… AND run_state = 'running')` predicate, so every guard **fails closed when the
  associated run does not exist** as well as when it is not `running`. The UPDATE guard checks **both**
  the OLD and the NEW associated run, and holds `selection_run_id`, `snapshot_id`, and `cik_numeric`
  **immutable**, so a disposition row can never be moved between runs, between snapshots, between
  selected target entities, or from a `running` run onto a terminal one. `recorded_at_utc` may be
  updated while the same run remains `running`; rows are immutable once it leaves `running`;
- **one additive feasible-transition trigger, whose complete SQL is also frozen in Decision 020 §8.2**,
  requiring every selected entity, controls included, to have exactly one reserve disposition before
  `running -> feasible`;
- **no policy-reference row**, and **no edit, replacement, or reinterpretation** of migrations `0009`,
  `0010`, or `0011` — every trigger it adds is new and collision-free, and their inherited OLD-only and
  NULL-comparison behaviour is deliberately left untouched.

**The four trigger definitions in Decision 020 §8.2 are normative, frozen, and approved.** An
implementation session **reproduces that SQL verbatim**; trigger behaviour is not defined by prose
anywhere in this contract, and **no implementation-time reinterpretation, reformulation, optimization,
or "equivalent" rewriting of that SQL is permitted**. A difference between migration `0012` and the
frozen §8.2 SQL is a defect in the migration, never a correction to the decision record.

**Migration `0012` was created, reviewed, and accepted.** Its exact DDL passed the focused independent
**governance** re-review that preceded approval (2026-07-30), and the written migration then passed the
implementation and acceptance reviews under "Independent review stages" — the final acceptance review
confirmed its statement region is byte-identical to the frozen §8.2 SQL, that it adds exactly one
`STRICT` table and four triggers, and that it alters no existing object. **No migration other than
`0012` was or is authorized.** A schema gap discovered *during implementation*, beyond this authorized
migration, remained an owner-level conflict and a stop condition, never a migration a session may write
on its own; none was found.

## Lifecycle and transaction behavior

- **One explicit transaction per run attempt**, unchanged from S5.2. The lifecycle row, its single
  `planned -> running` event, every result row, every contribution and member row, and every reserve
  row commit together or not at all.
- **The `running -> feasible` transition is the last statement in that transaction.** Migration
  `0009` refuses every contribution, member, and reserve write once the run leaves `running`, and
  refuses `feasible -> running` outright, so there is no second window and no reopening.
- A non-feasible run persists **no** reserve, contribution, or member row — the schema requires zero
  durable result rows before a non-feasible terminal transition.
- Same-ID behavior, the retry prohibition, and the gate-failure rules are inherited unchanged from
  Decision 018 §18 and the accepted S5.3 same-ID integrity rule. **No retry entry point is added.**
- **Disposition rows are identity-immutable and fail closed.** Per the frozen SQL in Decision 020
  §8.2, a `pilot_selection_entity_reasons` row may never change its `selection_run_id`, `snapshot_id`,
  or `cik_numeric`; both the OLD and the NEW associated run must exist and be `running`; and a missing
  run aborts the write rather than silently passing. Foreign keys remain enabled and required.

## Reconstruction

Reconstruction re-derives the pure result, the membership, and the reserve packages from the frozen
snapshot under the run's own recorded seed, policy versions, and node limit, then validates every
persisted row against the re-derivation. It never trusts a stored value it did not re-derive, and it
fails closed on every condition in Decision 020 §10.

## Required tests

- **Membership:** deterministic and order-independent; exactly `provisional`-gated; the deferred quota
  contributes nothing; and the achieved-count invariant — recomputed counts equal the S5.1 diagnostics
  for every quota on every fixture.
- **Reserve construction:** deterministic rank under the accepted initial-selection tie-break;
  exact contribution-set equality with the target; cap and floor preservation; amendment-family and
  linked-amendment coverage preserved; role compatibility from frozen attributes; disjointness from
  the selected set; no duplicate replacement for one target; **exactly one package per target at rank
  1**; every selected entity including controls is treated as a target; **a replacement CIK serving
  two different targets is accepted**; and the reserve set is invariant under the order targets are
  processed.
- **Signature:** independently recomputed from normalized content on both sides and compared against
  the stored values — **not** a comparison of the two stored columns (Decision 016 §7).
- **Schema integrity, adversarially:** a subset, a superset, and an empty reserve contribution set each
  refused at the `running -> feasible` transition; a reserve written after `feasible` refused; a
  `feasible -> running` reopening refused.
- **Persistence and reconstruction:** every fail-closed condition in Decision 020 §10; partial reserve
  sets rejected; a non-feasible run persists zero reserve, contribution, and member rows; all three
  membership row families are written and reconstruct exactly.
- **No-compatible-reserve:** the outcome is target-specific, review-required, nonblocking, and does
  not make the run infeasible or node-limit-exhausted; and it is durably recorded in
  `pilot_selection_entity_reasons` with `reason_scope = 'reserve'` and
  `reason_code = 'REVIEW_PILOT_NO_COMPATIBLE_RESERVE'`.
- **Migration `0012`, adversarially:** the new table is `STRICT`; its composite foreign key rejects a
  CIK that is not a selected entity of that run and snapshot; its primary key rejects a duplicate
  disposition row for one target; its `reason_code` foreign key and reserve-scope CHECK reject an
  unauthorized scope and an unauthorized code; and the migration is contiguous, provenance-recorded,
  byte-immutable, and idempotent under rerun per repository convention. **These are the owning
  enforcement boundaries** for duplicate dispositions and unauthorized scope/code under Decision 020
  §8.3 — prove them here, not at the feasible transition. The migration must also be **byte-faithful to
  the frozen Decision 020 §8.2 SQL**.
- **Lifecycle guards, adversarially:** INSERT into a non-running run rejected; INSERT into a *missing*
  run rejected (fail-closed); DELETE from a non-running or missing run rejected; UPDATE with the OLD
  run `running` and the NEW run `feasible` **rejected**; UPDATE between two concurrently `running`
  runs rejected because target identity is immutable; UPDATE changing `snapshot_id` rejected; UPDATE
  changing `cik_numeric` rejected; UPDATE of `recorded_at_utc` alone, while the same run remains
  `running`, accepted; and every update and delete rejected once the run reaches a terminal state.
- **Feasible-transition disposition, exhaustively over every constructible invalid state.** Each of the
  following refuses the `running -> feasible` transition: a selected entity with **neither**
  disposition; one with **both** disposition types; a target with a **rank-2 reserve only**; a target
  with **rank-1 plus rank-2**; a **control** target with no disposition; and **one missing disposition
  among many selected entities**. A run in which every selected entity, including every control, has
  exactly one disposition is accepted. The rank-2-only case is load-bearing: its disposition count is 1,
  so only the rank condition rejects it.
