## 9. Request-plan and ceiling controls

- The run **consumes** the approved plan; it never re-derives or recomputes one mid-window
  (master plan M3.2 §15).
- `m3 acquire` requires `--plan` (matching hash `19be7bdc…`), `--window M3.2A`, an explicit
  `--live` flag with no default, and `--ceiling 801` exactly equal to the approved integer; a
  mismatch on any of these refuses before any transport construction.
- The shared cumulative physical-attempt ceiling gate (`sec.request_ceiling`) is supplied
  explicitly — never defaulted or inferred — and **refuses the attempt that would exceed 801**:
  stop-before-overflow, never stop-after. A complete run may finish exactly at 801; equality with
  planned work remaining is `stopped_at_ceiling`, records `SEC_REQUEST_CEILING_EXHAUSTED`, and is
  a Gate H failure. The ceiling is **never raised mid-window**; more headroom requires stopping,
  re-planning, and a new owner approval.
- Every retry, redirect hop, and controlled post-cooldown request consumes one physical attempt;
  the accepted response policy applies unchanged (5 transient retries, 60 s backoff ceiling,
  `Retry-After` honoured when usable, one 600 s aggregate cooldown with one controlled further
  request, second cooldown terminal; retryable statuses 408/500/502/503/504; failure never becomes
  an empty success).
- Actual counts are recorded per route and reconciled item-by-item against the plan at Gate H; a
  deviation is a finding, not a variance.

## 12. Interruption, restart, and recovery

Per master plan M3.2 §§27–29, `interrupted_run_recovery.md`, and accepted Decision 051: on
interruption, stop new requests; preserve every attempt and committed object; quarantine
partial/unverifiable objects only under separate mutation authority; roll back the uncommitted
transaction; rebuild the projection only under accepted recovery authority; run integrity and FK
checks; write the terminating receipt where the process remains able to do so; **require an explicit
owner resume-or-new-run decision**. Resume only after the read-only inspector (`m3 recovery-state`)
reports `SAFE`, duplicate prevention is proven, and a valid predecessor receipt exists; the
consumed physical-attempt count carries forward under the same ceiling; a resumed receipt names its
predecessor.

**Current recovery semantics (Decisions 062, 063, and 064).** The paragraph above states the
lifecycle; four rules govern how it is evaluated now:

1. **Condition 8.2** asks whether the terminal *or* interruption state is **established, not
   guessed** (Decision 062 §3, extended by Decision 064 §3 to a successful `complete` head). A
   successful head is reported as what it is, is never called a failure, and never acquires a
   fabricated interruption state.
2. **`SAFE` is evidence certainty, never permission to acquire again** (Decision 064 §4). A
   completed window is `SAFE` with continuation **refused**; `m3 acquire --resume-from` against a
   `complete` receipt refuses before a transport is constructed.
3. **Condition 8.12** cross-checks the carry-in against the receipt chain's **root**, not its head
   (Decision 064 §2), so a lawful plan transition does not read as a disagreement. **Condition 8.10**
   still asks about the head's plan.
4. **`rebuild-projection`** has an action-specific eligibility gate (Decision 064 §5): it repairs a
   projection that *lags* authoritative SQLite and refuses one that *diverges* from it, and store
   uncertainty is adjudicated before the derived projection is reconstructed. No other recovery
   action inherits that gate.

The predecessor receipt of a chain is located by its **recorded identity** among the accepted
receipt artifact locations beneath the governed evidence root, never by assuming it sits beside the
head (Decision 063).

**Exact evidence and conservative reservation (Decision 051's narrow amendment of Decision 032 F3
and Decision 040 §7):**

1. Exact, accepted, independently verifiable durable evidence controls when it establishes the
   physical-attempt count without inference. No attempt segment is counted twice.
2. For the interrupted initial T5 invocation, the verified immutable raw lineage plus the sequential
   acquisition path establishes exactly **1 consumed physical attempt of 801**. No historical
   `ops_retrieval_attempts` row or receipt is backfilled.
3. For future sends, `ops_retrieval_attempts` is the primary durable consumed-count surface. One
   `started` row commits **before each physical transport send**; if that commit fails, no send
   occurs; every committed `started` row counts as consumed even if termination occurs before the
   transport call; each retry and redirect send has its own row; terminal state is updated when
   deterministically possible, and a stranded `started` row remains consumed.
4. Receipts, committed observations, raw lineage, and transport-response accounting reconcile with
   that ledger. An irreconcilable disagreement is `UNDETERMINED`.
5. Only when the exact count for at most one identifiable in-flight logical request is genuinely
   unrecorded, unattributable, or ambiguous is the full registered per-route `A_reachable` charged.
   If the logical request, route bound, or number of possible in-flight requests cannot be
   established, the determination is `UNDETERMINED`.

**Receiptless inspection does not mean receiptless continuation.** Decision 051 permits a future
explicit, read-only first-invocation receiptless inspection mode, bound to the exact interrupted run
identity. It can establish facts and consumed count but can never report `SAFE`, propose
continuation, enable `--resume-from`, or mutate state. A missing or mistyped ordinary receipt path
remains an error. Decision 050 §8's predecessor-receipt requirement remains fully binding for every
resume.

**Receiptless ledger coverage is decided globally, one-to-one (Decision 055 §8, ruling 055-D).**
Across **all** owned receiptless lineage segments, a durable `ops_retrieval_attempts` reservation
may satisfy **at most one** segment. The determination is `UNDETERMINED` on unmatched cardinality,
multiply matchable cardinality, duplicate reservation reuse, source/URL/run mismatch, a leftover
contradiction, or **any inability to establish an exact bijection** — in particular, one reservation
against two owned same-URL segments is `UNDETERMINED`, never a consumed count of 1 with `UNSAFE`.
This corrects the per-manifest evaluation recorded as **M3-L14**; selecting and implementing the
correction does not close that entry.

**One-use clean-root carry-in (Decision 055 §6, ruling 055-B — a narrow addition to this section).**
This section otherwise recognizes only predecessor-receipt carry-forward. Decision 055 adds exactly
one further way a run may begin from a non-zero consumed baseline, and **it is never a resume**:

- one explicit CLI interface, `m3 acquire --carry-in-authority`, which **refuses coexistence with
  `--resume-from`** before any transport is constructed;
- carried by a canonical-JSON artifact under schema `m3-carry-in-authority/1.0`, supplied by a **safe
  relative path beneath the governed evidence root** under the existing escape-refusing discipline,
  and **identified by the SHA-256 of its exact canonical bytes** (no self-hash field inside it);
- binding, all mandatory, and compared **literally against the accepted values** rather than only
  for internal consistency: window `M3.2A`; the frozen request-plan SHA-256; the cumulative ceiling
  `801`; the historical seed `1`; the allocation of that one attempt to `sec_bulk_submissions`,
  compared as a whole mapping so a substituted, extra, or omitted route is refused; the
  `Decision 055` identity; the authorized new run id; and the later accepted orphan-adoption
  decision and evidence identities — the decision reference a canonical `Decision NNN` that is not
  Decision 055 itself, and the evidence identity a lowercase 64-hex SHA-256. A self-consistent
  artifact naming a different seed, plan, ceiling, route, or decision is **refused**: an artifact's
  author controls the artifact, so self-consistency proves nothing about authorization;
- **parsed, canonicalized, hashed, and validated before transport construction**, and refused there
  on replay, run-id mismatch, plan/window/ceiling/seed/route mismatch, malformed or noncanonical
  bytes, a missing binding, an unsafe artifact path, or a conflicting resume;
- **re-proved from the authority object itself at every production execution and consumption
  boundary**, not only where bytes are read. The authority type is publicly constructible and its
  mappings are ordinary Python values, so "the artifact gate ran" is a fact about a code path
  rather than about the value a driver is holding. Each boundary therefore re-proves the fixed
  bindings above **and** that the object's `authority_sha256` is the SHA-256 of the canonical
  closed document its own bindings form. The identity is what makes the bindings unforgeable: the
  fixed values are public constants a hand-built object can copy, but a digest over the whole
  document cannot be invented, and any post-admission mutation — including of the route mapping —
  moves the document away from the identity it carries. A directly constructed or mutated
  authority therefore reaches neither the run registration, nor the consumption checkpoint, nor
  the transport;
- **consumed exactly once** by a deterministic `ops_checkpoints` primary key keyed by that SHA-256,
  inserted in the **same existing `BEGIN IMMEDIATE` transaction** as new-run registration — **no
  migration**; both rows commit or neither exists. The durable checkpoint is the canonical
  serialization of a closed nine-field document, and the recovery cross-check reads it as one:
  bytes that merely parse to the right fields, an allocation count that is not a non-negative
  integer, or any departure from the fixed Decision 055 values above is `UNDETERMINED`, and
  agreement between the checkpoint and the root receipt does not substitute for it;
- **burn-before-wire**: a later pre-wire failure after that commit leaves the authority **consumed
  even with zero attempts placed**. There is **no automatic reissue, retry, or replacement** — a
  replacement authority is a new owner act.

**An M3.2A live acquisition states the baseline it begins from, or it does not run.** M3-L16 lists
a run observed starting its consumed count at zero as a stop condition, so exactly one baseline
source is required and the two are mutually exclusive: the one-use carry-in authority for a clean
root, **or** a valid continuation for a resume. Supplying **both** is refused because a carry-in is
never a resume; supplying **neither** is refused because there is no zero-baseline default. The
refusal is decidable from the operator's arguments alone, so it happens before the operational
catalog is created, before storage is prepared, and before any transport could be constructed — and
is re-asserted at the acquisition driver, before run registration, so a caller several frames away
cannot reach the transport with a zero baseline. It is scoped to **M3.2A**: other windows have no
historical consumption to carry, and their ordinary zero-baseline roots and receipts stay lawful.

The predecessor-receipt requirement of Decision 050 §8 is untouched: it remains fully binding for
**every resume**, and a carry-in root is not a resume. The global `PhysicalAttemptCeiling` is
constructed with `approved_ceiling` **801** and `consumed` **1**; cumulative consumption is that seed
plus new durable reservations, and there is **no `802`, additive, shadow, or reset ceiling**. Route
attribution is **evidence and reporting only**: the remaining bulk-route headroom of **5** is an
accounting figure and **never a runtime refusal**, and the global ceiling remains the sole runtime
enforcement. The frozen plan and its 75 logical requests are unchanged, there is **no pre-run fit
gate**, and it remains lawful for the ceiling to stop the run at cumulative 801 with planned work
remaining.

**M3-L16 still blocks every clean-run and live authorization.** The mechanism above is implemented
and tested, not accepted: a clean carry-in run additionally requires the separately authorized,
offline, one-time, **verified orphan adoption** of Decision 055 §9 (Path B) to have executed and been
accepted with zero unresolved historical orphan mismatch. Until then a clean run, transport
construction, network use, and SEC contact remain prohibited.

**Recovery uncertainty is a stop condition.** The interrupted initial T5 invocation is permanently
non-resumable and remains `UNDETERMINED` pending separately authorized disposition; its eventual
truthful terminal job state is `stopped`, but Decision 051 does not authorize that mutation. Nothing
acquired is ever deleted.

## 14. M3.2A termination, successful completion, and Gate H

**Termination.** M3.2A **terminates** when every planned logical request has reached a terminal

required object is present in the raw store, hash-verified, and fully provenanced** — the

quarterly-index instances; **any planned request whose terminal disposition left its required
object absent** (an absent-evidence `404`, a quarantined body, or any terminal failure) **is
enumerated in the window's receipt and expressly adjudicated by the owner before the
between-windows freeze and before any M3.2B budget approval** — a window with any unadjudicated
required-object absence is `completed_with_absences`, is **not** successfully complete, and is

(`actual ≤ ceiling`, zero overflow); zero prohibited-route attempts; zero unresolved blocking
drift; network disabled again; every receipt validated; and the between-windows freeze recorded
the exact bootstrap object identities.

windows: per-window planned-versus-actual reconciliation, raw-store and provenance completeness,

item passes: `M3_2_METADATA_ACQUISITION_COMPLETE_GATE_H_PASSED`.
