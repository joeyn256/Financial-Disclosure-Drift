## 11. Snapshot-freeze semantics

- **What makes a snapshot frozen:** the `building -> frozen` transition, permitted only by migration
  `0009`'s `pilot_snapshot_transition_guard`, and gated by `pilot_snapshot_freeze_requires_valid_state`
  (declared entity and accession counts equal to the actual rows; exactly one anchor per accession)
  and by the row `CHECK` requiring `frozen_at_utc` and all nine content digests to be non-`NULL`.
- **Every Decision 019 §9 obligation must be validated at freeze**, and again at read time, and each
  must fail for its own stated reason rather than incidentally (rehearsal scenario E2).
- **A frozen snapshot is immutable.** `pilot_snapshot_frozen_fields_immutable` holds all 22 content,
  policy, coverage, hash, and provenance fields, including across `frozen -> invalidated`;
  `pilot_snapshot_no_delete` refuses deletion of a `frozen` or `invalidated` row.
- **A wrong snapshot is superseded by a new one under explicit authorization, never edited** (master
  plan M3.3 §27).
- **Canonical snapshot identity** is `snapshot_id`, content-derived and excluding `census_run_id`
  (Decision 016 §1), at the preimage **OR-1** fixes in §10.1.

**Interruption, atomicity, and supersession are fixed by R5** (§1.1). In particular: the whole
construct-and-freeze operation is one authoritative transaction that rolls back entirely on any
failure, leaving **no** partial authoritative snapshot; a `building` row found at entry from an
abnormal or pre-existing condition is **nonauthoritative and blocks execution pending owner
disposition**, and is never automatically resumed, completed, repaired, invalidated, or superseded;
and replacing a wrong or obsolete frozen snapshot requires new explicit owner authorization and the
accepted invalidation/supersession lifecycle. There is **no automatic recovery across any
authoritative M3.3 boundary**.

## 13. Persistence, reconstruction, and equality

**Persistence.** One `running` window per S5 run, ending at `running -> feasible` as the last
statement of one transaction. Reserves, contributions, members, quota results, and dispositions are
written inside that same window (Decision 020 §7). Exactly one `proposed` manifest row, written
atomically with its document (Decision 021 §11.3).

**Equality that must be proven.** Three states must agree, and nothing stored is trusted that was
not re-derived (Decision 021 §12):

1. **Selected result → persisted state.** Every persisted component is validated against the
   re-derived pure result; a corrupted, incomplete, contradictory, or policy-mismatched persisted run
   raises `GateFailureError`.
2. **Persisted state → independently reconstructed state.** `reconstruct_persisted_joint_selection`
   re-derives the result from the same frozen snapshot under the run's own recorded seed, policy
   versions, and node limit, and compares **field by field** through the single centralized
   `JointSelectionRunIdentity` comparison — order-independent, with **neither public entry point more
   permissive than the other**.
3. **Persisted rows → every governed identity.** Each of the eight component digests,
   `selection_result_sha256`, `root_manifest_sha256`, and `manifest_id` is recomputed **from
   persisted rows, never from memory**, and compared; the document is re-rendered and re-serialized
   byte-identically; verification is item by item over all 81 crosswalk items.

Any difference at any layer is a `GateFailureError`. **Reconstruction repairs nothing**, and stored
identity corruption is a stop-and-report condition.

## 14. Write-free replay

Replay **reads, reconstructs, compares, and returns** (Decision 021 §§11.3, 12). It issues no
`INSERT`, `UPDATE`, `DELETE`, `INSERT OR REPLACE`, `REPLACE INTO`, or `INSERT OR IGNORE` against
`pilot_manifest_versions` or `pilot_selection_runs`; migration `0013` triggers 5 and 6 refuse one if
it were ever issued. An identical re-seal is idempotent; a differing seal is refused. Rehearsal E8
additionally requires persisted state **byte-identical before and after each replay**, with the
receipt the only thing that differs between two replays.

**The proof standard is fixed by R3** (§1.1), and it is **durable-byte equality**: every pre-existing
durable artifact, the main SQLite database file included, is byte-identical before and after. Transient
`-wal`/`-shm` sidecars are not that equality target and remain separately governed — never a licence
to change the main database's bytes. Every M3.3 read-only path — candidate-source read, independent
reconstruction, replay, manifest verification, independent verification — must use a **true OS-level
strictly-read-only connection** (`SQLITE_OPEN_READONLY`, cannot checkpoint); a logical `query_only`
convention on an OS-level read-write handle is **insufficient**, and `read_only_connection`
(`storage/catalog.py`) is therefore not admissible for a governed M3.3 read. **No read-only M3.3 path
acquires a writer lease**, and no read-only M3.3 action may checkpoint or otherwise alter the main
database. If an active writer, a lease, or any other condition prevents proof of write-freedom,
**fail closed**.

**Pre-I/R hardening is fixed by R8** (§1.1). Before M3.3 rehearsal can be accepted, every existing
reusable code path **actually used** by M3.3 for a governed read-only action must satisfy R3; where a
required shared path still opens an OS-level read-write handle, M3.3-I/R is authorized later to
harden **that path narrowly**. **No repository-wide cleanup of unrelated M2/M3.2 call sites**, and no
separate infrastructure project. The candidate inventory is in
[`Docs/m3/m3_3_governance_foundation_inventory.md`](../../Docs/m3/m3_3_governance_foundation_inventory.md)
§K, CF4; it is an inventory, and R8 — not that document — is the authority for what must change.

## 17. Atomicity

- **One explicit transaction per manifest write** — row and document commit together or not at all.
  A fault leaves **no** new row and **no** new file; a **pre-existing** artifact at the
  content-derived path is outside the transaction's ownership and is not deleted (**D023-O3**).
- **Sealing is a separate, prior transaction** (§15).
- **A failed selection leaves the run in its recorded failed state — it is not deleted**, and no
  automatic retry occurs (Decision 018 §18).
- **A failed freeze leaves no partial snapshot**, because the whole construct-and-freeze operation is
  one authoritative transaction that rolls back entirely on any failure (**R5**).
- **Partial authoritative state fails closed** at every boundary, and **no automatic recovery crosses
  an authoritative M3.3 boundary** (**R5**). Sealing is a separate hard boundary from manifest
  construction: a valid sealed selection may exist with **no** manifest, and that state authorizes
  **no** automatic manifest construction.

## 32. Failure, rollback, and recovery

A failed manifest write leaves **no** row and **no** new file; a pre-existing artifact at the
content-derived path is not deleted (**D023-O3**). A failed selection leaves the run in its recorded
failed state — it is **not** deleted, and no automatic retry occurs. A frozen snapshot is immutable;
a wrong one is superseded under explicit authorization, never edited. **Nothing acquired in M3.2 is
touched.** Recovery uses
[`Docs/m3/templates/interrupted_run_recovery.md`](../../Docs/m3/templates/interrupted_run_recovery.md)
and the enumerable safe states migration `0013`'s guards establish (master plan M3.3 §28); identical
restatement is idempotent, and anything else is a stop condition. **R5** governs the snapshot-freeze
boundary: the whole construct-and-freeze operation rolls back as one, and a `building` row surviving
from an abnormal or pre-existing condition is nonauthoritative and blocks execution pending owner
disposition.
